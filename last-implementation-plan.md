# План улучшений поиска, PDF и UI

## Context

Нужно довести активное рабочее дерево `document-searcher` до согласованного поведения на Windows и Linux/ALT Linux. Сейчас фильтры логирования по умолчанию пропускают `INFO`, Windows UI показывает расширения постоянными chips, GTK UI не синхронизирован с изменённым `WorkerCommand::Scan`, а CLI получает весь `Vec<SearchMatch>` только после завершения поиска. PDF-пайплайн умеет извлекать текстовый слой и выполнять полный OCR fallback, но для смешанного PDF принимает решение об OCR по суммарному тексту документа: отдельная сканированная страница может быть пропущена. Ошибка с URI `file:///...#page=N` и `ShellExecuteW code 2` требует не передавать неподдерживаемый page-URI напрямую в ShellExecuteW и всегда иметь рабочий fallback на обычный путь.

Все существующие незакоммиченные изменения сохраняются; реализация выполняется после одобрения этого плана. Windows-проверки не выдаются за проверку GTK/Linux, а наличие внешних OCR-инструментов и поведение конкретного PDF viewer проверяются отдельно.

## Рекомендуемый подход

### 1. Логирование

- В `src/app_win.rs` и `src/app.rs` заменить fallback `EnvFilter` с `info` на `warn`, чтобы обычный запуск показывал только `WARN` и `ERROR`.
- Удалить или понизить startup-сообщение `tracing::info!` в Windows UI; не оставлять штатных INFO-событий в коде.
- Сохранить явный `RUST_LOG` как диагностическое переопределение, но проверить штатный профиль поиском по `tracing::info!` и запуском CLI/GUI.

### 2. Единый контракт расширений и меню

- Устранить рассинхронизацию между `scanner.rs::ALL_SUPPORTED_EXTENSIONS` и `extractor.rs::TEXT_EXTENSIONS`: вынести общий список поддерживаемых расширений и список plain-text расширений в общий модуль констант либо в существующий модуль модели, после чего импортировать его из scanner/extractor/UI.
- Добавить единое нормализующее правило для расширений: убрать начальную точку, привести к согласованному регистру, удалить дубли и отклонять расширения, которых нет в поддерживаемом списке. Не разрешать пустой выбор; сохранить дефолт `docx,pdf`.
- В Windows HTML UI (`app_win.rs`) заменить постоянный ряд chips на компактную кнопку с иконкой трёх полосок и доступным tooltip/label. По нажатию открывать dropdown/popover с checkbox-элементами для `docx`, `pdf` и поддерживаемых текстовых форматов; добавить закрытие по клику вне меню и клавиатурному `Escape`.
- Состояние активных расширений получать из `/api/state`, а не держать только в JS-хардкоде. `/api/set-extensions` должен обновлять `AppState.scan_extensions`, запускать сканирование с явным списком и не использовать `DOCUMENT_SEARCHER_EXTENSIONS` как канал состояния UI.
- Для GTK (`app.rs`) добавить `gtk::MenuButton`/`Popover` с checkbox-элементами и использовать тот же список расширений. При изменении выбора обновлять `AppState.scan_extensions` и запускать сканирование с копией списка. Обновить оба существующих вызова `WorkerCommand::Scan` (начальный скан и выбранная папка), чтобы они передавали `extensions`.
- Оставить переменную окружения только совместимым CLI/legacy-механизмом; явно переданные расширения должны иметь приоритет и не зависеть от глобального `set_var` во время работы UI.

### 3. Надёжное извлечение PDF, включая смешанные страницы

- Сохранить текущую иерархию fallback `lopdf` → `pdf-extract` → OCR при невозможности загрузить/распарсить PDF, но изменить критерий принятия решения на постраничный.
- В `extract_pages_from_lopdf_document` сначала извлекать каждую страницу через существующий `extract_single_page_text`. Для страницы с пустым или слишком малым содержимым отдельно запускать OCR только этой страницы; текстовые страницы не должны повторно OCR-иться.
- Реализовать переиспользуемый OCR helper для диапазона страниц: рендерить через `pdftoppm` с `-f/-l`, распознавать только нужную страницу Tesseract, нормализовать результат и гарантированно удалять временные файлы. При наличии нескольких слабых страниц по возможности выполнить один рендер PDF и распознавать только соответствующие изображения, чтобы не запускать процесс на каждую страницу без необходимости.
- Сохранить точный номер страницы в `ExtractedPage`/`SearchOccurrence`. Для Windows WinRT fallback вернуть постраничные результаты с явными разделителями/метаданными либо честно сохранить ограничение `page=1`, если конкретная среда не позволяет получить границы страниц; не подменять это гарантией deep-link.
- Применить `normalize_whitespace` единообразно к plain text, DOCX, `pdf-extract` и OCR-результатам, не ломая границы страниц и UTF-8 offsets. Не считать PDF полностью обработанным только потому, что на другой странице уже найдено 32 алфавитных символа.
- Все ошибки отдельной страницы логировать как `WARN` и продолжать обработку остальных страниц; возвращать ошибку только если не удалось получить ни одного пригодного результата и отсутствуют fallback-пути. Не допускать panic на повреждённых пользовательских PDF.

### 4. Потоковый CLI на уровне ядра

- В `src/model/search.rs` выделить переиспользуемую обработку одного файла и добавить библиотечный `search_files_streaming` с callback (или эквивалентным синхронным каналом). Callback вызывается сразу после нахождения всех вхождений одного файла и получает `SearchMatch`; ошибки извлечения конкретного файла остаются `WARN` и не останавливают весь поиск.
- Сохранить существующий `search_files` как пакетную обёртку, собирающую результаты из streaming API, чтобы не ломать тесты и worker-контракт.
- В `main.rs::print_search` печатать заголовок до поиска, затем каждый файл и его вхождения сразу в callback, а итоговое количество после завершения. Использовать тот же явно выбранный список расширений, который использовался для сканирования.
- Вывод должен быть последовательным и безопасным для stdout; ошибка записи/поиска возвращается вызывающему коду. Не переносить в CLI debounce или GUI-специфичную отмену из `Worker`; уже существующий `WorkerEvent::SearchResultFound` оставить для UI.
- При необходимости worker должен использовать выделенную обработку одного файла, но не дублировать PDF/search-логику.

### 5. GTK-паритет общего воркера

- В `app.rs::Ui` добавить обработку одного `SearchResultFound`: append/merge результата, обновление списка и сохранение пагинации. На `SearchCompleted` не затирать уже показанные streaming-результаты пустым финальным `Vec`.
- Согласовать переходы состояний `SearchStarted`, `SearchProgress`, `SearchResultFound`, `SearchCompleted`, `SearchCancelled` и фильтрацию устаревших запросов с текущим Windows UI настолько, насколько это возможно в общем событийному контракте.
- GTK сборку проверять только в окружении с `pkg-config`, GTK4 и libadwaita; отсутствие этих системных библиотек на Windows фиксировать как ограничение среды, а не как подтверждение ошибки исходников.

### 6. Открытие PDF и `ShellExecuteW code 2`

- В `app_win.rs::open_file_at_page` оставить проверку whitelist текущего индекса, нормализацию `\\?\` пути и проверку существования файла.
- Не передавать `file:///...#page=N` как обычный аргумент `ShellExecuteW`: это и вызвало наблюдавшийся `code 2` у ассоциации/обработчика URI. Если сохранится попытка viewer-specific page URI, вынести её в отдельный путь, проверить код результата и при любой ошибке немедленно повторить открытие чистого файлового пути через `open_with_default_app`.
- Всегда возвращать понятную ошибку только после неудачи обычного открытия; в WARN указывать путь и запрошенную страницу. В UI показывать номер страницы, но не обещать универсальный переход: поддержка `#page=N` зависит от конкретного PDF viewer (в частности, Yandex Browser может его игнорировать).
- Не возвращать HTTP `200 OK` как будто открытие удалось, если обе попытки завершились ошибкой; сохранить защиту от открытия файла вне текущего индекса.

## Критические файлы

- `src/src/model/{constants,scanner,extractor,search,actions,worker,state}.rs`
- `src/src/main.rs`
- `src/src/app_win.rs`
- `src/src/app.rs`
- `src/Cargo.toml` только если для тестового/структурного решения потребуются новые зависимости

## Проверка

1. До и после изменений: `cargo fmt --check`, `cargo clippy --lib --tests --no-default-features -- -D warnings`, `cargo test --lib --no-default-features`.
2. Windows профиль: `cargo clippy --all-targets --features windows-desktop -- -D warnings` и `cargo test --bins --features windows-desktop`.
3. GTK профиль: `cargo check --all-targets --features desktop` в Linux/ALT Linux окружении с установленными GTK4/libadwaita/pkg-config; на текущем Windows отдельно зафиксировать, если системные зависимости отсутствуют.
4. Добавить unit-тест streaming API: callback получает результаты по одному в порядке завершения последовательного ядрового прохода, пустой запрос не вызывает callback, ошибка одного файла не прерывает остальные.
5. Добавить PDF fixtures/integration-проверки для текстового PDF, полностью сканированного PDF и смешанного PDF (текстовая страница плюс image-only страница), включая номера страниц и нормализацию. OCR-тесты запускать только при доступных `pdftoppm`/Tesseract или WinRT и явно отмечать пропуск при их отсутствии.
6. Проверить Windows UI вручную: dropdown-гамбургер, сохранение выбора после `/api/state`, пересканирование, постепенное появление результатов, открытие обычного PDF и корректный fallback при невозможности открыть page URI.
7. Выполнить `git diff --check`; не считать Linux/ALT Linux, OCR или поведение Yandex Browser проверенными без соответствующей среды/инструментов.
